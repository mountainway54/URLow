# 架構設計與技術選型

這個專案一開始只要求做出縮網址的主要流程。我先把範圍定在四件事：建立短網址、開啟短網址、用密碼管理連結，以及把成品部署上線。報表、自訂短碼和使用者帳號不在這次範圍內。

## 一次請求怎麼走

建立短網址時，Server 會驗證原始網址，產生 8 字元短碼，再寫入 PostgreSQL 和 KV。有人開啟短網址時，Worker 先查 KV；沒有快取才透過 Hyperdrive 查 PostgreSQL。

```text
瀏覽器
   │ GET /{code}
   ▼
Cloudflare Worker
   ├── KV 有資料 ──────────▶ 302 / 404 / 410
   │
   └── KV 沒資料 → Hyperdrive → Neon PostgreSQL
                                      │
                                      └──▶ 302 / 404 / 410 / 503
```

前端只負責收集輸入和顯示結果。網址是否合法、密碼是否正確、短碼是否重複，都要由 Server 再檢查一次，不能只相信瀏覽器送來的資料。

## 為什麼用 Nuxt

Nuxt 可以把頁面和 Server API 放在同一個專案。對 URLow 這種規模來說，這比拆成兩個專案省事：不用維護兩套建置和部署設定，前後端的型別也比較容易對照。

頁面放在 `app/`，API 與 Redirect 放在 `server/`。正式建置使用 Nitro 的 `cloudflare_module` preset，輸出可以直接交給 Cloudflare Workers。

## TypeScript 怎麼用

我原本比較熟 JavaScript，所以沒有一開始就追求複雜型別。表單狀態大多讓 TypeScript 自動判斷；API response、資料庫資料、錯誤碼和 Cloudflare bindings 則明確定義。

專案目前用到 `interface`、聯集型別、泛型和 `Pick`、`Partial` 等 utility types。外部資料先以 `unknown` 接收，通過 Zod 或自訂 type guard 後才使用。詳細範例整理在[專案技術與部署](./專案技術與部署.md)。

## 資料怎麼保存

Neon PostgreSQL 是正式資料來源。`short_urls` 資料表保存：

- 原始網址與唯一短碼
- 管理密碼的 bcrypt hash
- 私人備註與啟用狀態
- 建立及更新時間

Drizzle ORM 負責 schema、migration 和查詢型別。資料庫的 unique constraint 會擋下重複短碼；若真的碰撞，建立流程最多重試五次。

KV 只拿來加快 Redirect，不是正式資料來源。讀取方式、負向快取和同步失敗的處理寫在[此專案的 KV 實作細節](./此專案的KV實作細節.md)。

## 輸入驗證與 API 文件

API request body 先經過 Zod。原始網址必須是完整的 `http://` 或 `https://` URL，備註有長度限制，管理密碼則要符合字元數與 UTF-8 bytes 限制。

同一份 Zod schema 也用來產生 OpenAPI 規格，Swagger UI 顯示的格式和 Server 實際驗證的規則來自同一處，少維護一份重複文件。

## Cloudflare 各自負責什麼

| 服務 | 用途 |
| --- | --- |
| Workers | 執行 Nuxt Server、API 和 Redirect |
| Workers Assets | 提供 CSS、JavaScript 和圖片 |
| KV | 保存 Redirect 快取 |
| Hyperdrive | 連接 Neon PostgreSQL |
| Rate Limiting | 限制管理密碼驗證次數 |

Cloudflare KV 是最終一致，修改後其他區域可能暫時讀到舊資料。API 會回傳快取同步結果和 stale window 提醒，程式不會假裝更新已經在所有地區立刻生效。

## 測試

Vitest 測試短碼、驗證規則、Service、API handler、資料庫 schema、KV cache 和 Vue 元件。整合測試另外確認 migration 後的資料表是否符合程式預期。

我也會用 Postman 與瀏覽器手動走過建立、管理、停用和 Redirect。自動化測試適合抓回歸，實際操作則能發現畫面和部署設定的問題，兩種都需要。
