# 專案技術與部署

這篇整理 URLow 用到的 Nuxt、TypeScript，以及部署到 Cloudflare Workers 的方式。我只寫專案裡真的有用到的部分，並說明它們各自解決什麼問題。

## 專案中用到的 Nuxt 功能

### 用檔案位置建立頁面和 API

Nuxt 會依照檔案放置的位置，自動建立對應的網址。以首頁為例，`app/pages/index.vue` 會變成 `/`；API 也是一樣：

| 專案檔案 | 對應網址 |
| --- | --- |
| `app/pages/index.vue` | `/` |
| `app/pages/api-docs.vue` | `/api-docs` |
| `server/api/short-urls.post.ts` | `POST /api/short-urls` |
| `server/api/short-urls/[code].patch.ts` | `PATCH /api/short-urls/:code` |
| `server/api/short-urls/[code]/management.get.ts` | `GET /api/short-urls/:code/management` |
| `server/api/health/database.get.ts` | `GET /api/health/database` |

檔名裡的 `[code]` 代表會變動的短碼。例如請求 `/api/short-urls/aB3xY8qP/management` 時，程式取得的 `code` 就是 `aB3xY8qP`。

這種做法少了手動設定 Router 的工作。看到檔案位置，大致就能知道它負責哪個網址。

### 前端和後端放在同一個專案

URLow 沒有另外建立一套後端專案。畫面放在 `app/`，API 和 Redirect 邏輯放在 `server/`：

```text
app/
├── pages/        頁面
├── components/   表單、按鈕等畫面元件
├── composables/  共用的 API 呼叫程式
└── assets/       CSS

server/
├── api/          API
├── middleware/   短網址 Redirect
├── services/     建立、管理、快取等功能
└── database/     資料庫連線與 Schema
```

`app/app.vue` 內的 `<NuxtPage />` 會顯示目前頁面。`<NuxtRouteAnnouncer />` 則會在換頁時通知螢幕閱讀器。

### Vue 的表單狀態

頁面元件使用 `<script setup lang="ts">`。表單輸入、錯誤訊息和載入狀態都用 `ref()` 保存：

```ts
const originalUrl = ref('')
const formError = ref('')
const isCreating = ref(false)
```

元件收到的資料用 `defineProps()` 宣告，按鈕或表單要通知外層元件時則使用 `defineEmits()`。這兩個功能都能直接加上 TypeScript 型別。

前端透過 `$fetch()` 呼叫自己的 API。例如建立短網址時，畫面會送出 `POST /api/short-urls`，再把回傳的短網址顯示給使用者。

### Nitro Server

Nuxt 的後端由 Nitro 處理。URLow 在 API 和 Middleware 中使用 H3 提供的工具：

- `defineEventHandler()`：接收 HTTP 請求。
- `readBody()`：讀取表單送來的 JSON。
- `getRouterParam()`：讀取網址中的短碼。
- `getRequestHeader()`：讀取管理密碼等 Header。
- `sendRedirect()`：回傳 `302 Redirect`。
- `setResponseStatus()`：設定 `404`、`410` 或 `503` 等狀態碼。

短網址 Redirect 寫在 `server/middleware/short-url-redirect.ts`。當有人開啟 `/{code}`，它會先查 Cloudflare KV，沒有結果才查 PostgreSQL。

### Nuxt 設定

`nuxt.config.ts` 裡最重要的是這行：

```ts
nitro: {
  preset: 'cloudflare_module'
}
```

它告訴 Nuxt：這個專案最後要在 Cloudflare Worker 執行，不是一般 Node.js Server。

設定檔也處理了兩個部署問題：

- 用 shim 取代 Worker 不支援的 `pg-native`。
- 保留 Cloudflare 提供的 `cloudflare:sockets`，讓 PostgreSQL 連線能在 Worker 使用。

Tailwind CSS 則透過 Vite plugin 載入。

## 專案中用到的 TypeScript 語法

我沒有把每個變數都寫上型別。一般表單狀態交給 TypeScript 自己判斷；API、資料庫和 Cloudflare binding 這類容易傳錯資料的地方，才會明確定義。

### `interface`：描述資料有哪些欄位

API 回傳的短網址資料用 `interface` 表示：

```ts
interface ShortUrlData {
  code: string
  originalUrl: string
  shortUrl: string
  note: string | null
  enabled: boolean
}
```

`ManagedShortUrlData extends ShortUrlData` 表示管理頁資料包含上面所有欄位，再多加建立和更新時間。共同欄位不用重寫一次。

### `type` 和聯集型別：列出可能的結果

Redirect 不一定成功，也可能找不到、已停用或資料庫故障：

```ts
type RedirectResolution =
  | { status: 302, targetUrl: string }
  | { status: 404 }
  | { status: 410 }
  | { status: 503 }
```

判斷 `status === 302` 後，TypeScript 就知道這筆資料一定有 `targetUrl`。其他狀態沒有這個欄位，若誤用會在編譯時提醒。

API 錯誤碼也用同樣方式列出允許的字串，例如 `VALIDATION_ERROR` 和 `DATABASE_UNAVAILABLE`，避免各處隨意拼出不同名稱。

### `?` 和 `null`：區分「沒傳」和「沒有內容」

```ts
interface CreateShortUrlBody {
  originalUrl: string
  managementPassword?: string
  note?: string | null
}
```

- `managementPassword?: string`：使用者可以不傳管理密碼。
- `note?: string | null`：可以不傳備註，也可以明確把備註清空。

更新資料時，這個差異很重要。沒傳代表不修改，`null` 則代表清除原本的值。

### 泛型：同一個外殼裝不同資料

每個成功的 API 都回傳 `{ data: ... }`，但 `data` 的內容不同：

```ts
interface ApiDataEnvelope<TData> {
  data: TData
}
```

`TData` 可以是新建的短網址，也可以是管理頁資料。共用的 request 函式只要寫一次，呼叫時再決定裡面是哪種資料。

### `Pick` 和 `Partial`：從現有型別挑出需要的欄位

管理頁只允許修改原始網址、備註和啟用狀態：

```ts
type UpdateShortUrlBody = Partial<
  Pick<ManagedShortUrlData, 'originalUrl' | 'note' | 'enabled'>
>
```

`Pick` 先挑出三個允許修改的欄位，`Partial` 再把它們變成選填。這樣只改備註時，不需要連網址和狀態一起送出。

專案也有使用 `ReturnType` 和 `Awaited`。前者取得函式的回傳型別，後者取得 Promise 完成後的資料型別。

### `unknown` 和型別檢查

API 錯誤、JSON 和 Cloudflare 環境變數都來自程式外部，不能直接相信它們的格式，所以先用 `unknown` 接住，再檢查：

```ts
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null
}
```

只有通過檢查後，程式才會讀取裡面的欄位。環境變數和 request body 還會再交給 Zod 驗證。

### 從 Zod 產生型別

Request body 的規則先寫在 Zod schema，再用下面的方式取得 TypeScript 型別：

```ts
type CreateShortUrlBody = z.output<typeof createShortUrlBodySchema>
```

修改驗證規則後，型別會跟著更新，比手動維護兩份相同欄位安全。

另外，`import type` 用來標記只在編譯時需要的型別；`satisfies` 則用來檢查物件是否符合指定格式，又不會丟掉原本的詳細型別。

## Cloudflare 部署

### 部署後有哪些東西

URLow 部署成一個 Cloudflare Worker。Nuxt build 會產生兩部分：

```text
.output/server/index.mjs   API 與 Redirect 程式
.output/public             CSS、JavaScript、圖片等靜態檔案
```

Worker 還會連接三個 Cloudflare 服務：

| Binding | 實際用途 |
| --- | --- |
| `HYPERDRIVE` | 連接 Neon PostgreSQL |
| `SHORT_URL_CACHE` | 保存短網址 Redirect 快取 |
| `MANAGEMENT_RATE_LIMITER` | 限制管理密碼的嘗試次數 |

這些名稱都設定在 `wrangler.jsonc`。程式用固定名稱取得服務，部署時 Wrangler 會把它們連起來。

### 為什麼使用 Hyperdrive

正式環境的 Worker 不直接保存 `DATABASE_URL`，而是透過 Hyperdrive 連接 Neon PostgreSQL。Hyperdrive 幫忙管理 Worker 到資料庫的連線。

資料庫 migration 不走 Hyperdrive。它是在部署前從本機讀取 `.env` 的 `DATABASE_URL`，直接連到 Neon 套用 schema 變更。

### 在本機測試 Worker

一般畫面開發可以使用：

```powershell
npm.cmd run dev
```

要連同 Worker、KV 和 Hyperdrive 設定一起測試時，使用：

```powershell
npm.cmd run db:migrate
npm.cmd run cf:dev
curl.exe -i http://127.0.0.1:8787/api/health/database
```

本機連線字串放在 `.dev.vars`：

```dotenv
CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE=postgresql://...?...&sslmode=require
```

`scripts/cf-dev.mjs` 會先檢查這個設定，再啟動 Wrangler。若連線字串不是 PostgreSQL URL、缺少 `sslmode=require`，或檔案出現其他不該有的變數，程式會直接停止。

### 正式部署步驟

```powershell
npm.cmd run db:migrate
npm.cmd run build
npx.cmd wrangler deploy --dry-run
npm.cmd run deploy
```

我把部署拆成以下步驟：

1. 先更新資料庫 schema。
2. 建置 Nuxt，確認程式可以正常編譯。
3. 用 Wrangler dry run 檢查 Worker bundle 和 bindings。
4. 部署 Worker 與靜態檔案。
5. 開啟首頁和 `/api-docs`，檢查資料庫健康狀態，再實際建立一個短網址測試 Redirect。

正式網站：[https://urlow.mw7.workers.dev/](https://urlow.mw7.workers.dev/)
